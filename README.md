# Crocaun Android

Отдельный Android-клиент для проекта [crocaun](https://github.com/infsofit/crocaun). Цель — совместимая передача файлов и текста, чат и история; копировать интерфейс Windows-программы не требуется.

> **Состояние:** реализован первый LAN-чат с совместимыми Windows параметрами шифрования, зашифрованной локальной историей и chat-вложениями. Основное Croc-ядро собрано в AAR в CI; пользователь подтвердил, что базовые отправка и получение Android↔Windows работают. Пакетная отправка через SAF, поиск Windows Crocaun в локальной сети для Croc-передачи, проверка публичных Croc relay и ручная подготовка файлов по абсолютным путям реализованы в текущей ветке, но требуют CI и проверки на реальных Android↔Windows устройствах. Пока нет фоновой службы, отмены передачи и прогресса по байтам; Internet/Nostr-чат и автоматический поиск собеседников для LAN-чата также не реализованы. APK остаётся debug-подписанным preview.

## Android и технологии

- Kotlin с нативным Android UI на Jetpack Compose.
- Минимальная версия — Android 11 (API 30). Целевая и compile-версия — Android 16 (API 36).
- LAN-чат подключается к Windows-клиенту по IP-адресу и TCP-порту `29014`. Для общего пароля комнаты используются те же PBKDF2-HMAC-SHA256 параметры, room ID, AES-256-GCM nonce/AAD и Base64 Raw Std формат, что и в Windows. Обмен — newline-delimited JSON с типами Windows `hello`, `rooms`, `have`, `m`, `get`, `file`.
- История чата хранится в app-private `files/chat-lan/history/` как JSONL из зашифрованных кадров. Пароли комнат на диск не записываются: после перезапуска нужно повторно ввести пароль комнаты, чтобы открыть её историю.
- Вложения чата выбираются и сохраняются через Android Storage Access Framework (`content://`). Чтобы Windows peer мог отдать вложение напрямую, исходник копируется в приватный каталог приложения, пока приложение запущено.
- Основная передача Croc в Windows использует Croc `v10.0.12` с Crocaun race-патчем. Это отдельный протокол от чата. `go-core/transfer` повторяет Windows password/relay mapping; AAR собирается и тестируется в CI, входит в APK и вызывается вне UI-потока. Android Send поддерживает несколько файлов через SAF и ручной ввод одного абсолютного пути на строку; файлы проходят проверку и копируются в приватный staging с Windows-совместимой уникализацией имён. Полученные файлы экспортируются через SAF.

## Что поддерживается и чего пока нет

Для чата можно вручную подключиться к Windows-узлу в доступной LAN/VPN, если TCP `29014` достижим с обеих сторон. Сообщения шифруются совместимым с Windows AES-GCM форматом. При одинаковом пароле комнаты Android и Windows вычисляют одинаковую комнату. Вложения чата предлагаются peer-у и скачиваются напрямую по TCP, как в Windows LAN chat. Для Croc-передачи Android умеет искать Windows Crocaun в режиме «Обмен» или «Ждать получателя в сети» по UDP `29008`. Выбранный peer задаёт прямой Croc relay; Windows объявляет его TCP-порт и резервные порты `29009–29013`. В Settings можно проверить публичные relay тем же ping/pong обменом, что и Windows.

Поиск Crocaun в LAN относится только к Croc-передаче: автоматический поиск собеседника LAN-чата пока не подключён, поэтому для чата по-прежнему нужен IP и TCP-порт. Ручные файловые пути принимаются по одному на строку. На Android 11+ прямой путь к общему хранилищу может быть закрыт Scoped Storage; при необходимости пользователь может отдельно открыть системные настройки и явно разрешить Crocaun `MANAGE_EXTERNAL_STORAGE`. Приложение не просит этот доступ при запуске. Это широкое разрешение ограничено [правилами Google Play](https://support.google.com/googleplay/android-developer/answer/10467955?hl=en); для выбора отдельных файлов предпочтителен SAF. Croc Send/Receive пока не переживают закрытие процесса, не поддерживают отмену, не показывают байтовый прогресс и не позволяют выбрать каталоги. Перед функциональным prerelease необходимо проверить на двух устройствах неправильный пароль, Unicode-имена, ошибку relay, отсутствие случайной перезаписи, пакетную отправку и LAN-режимы.

Android сейчас нацелен на API 36. Для приложений, нацеленных на API 37 и выше, Android 17 требует runtime-разрешение `ACCESS_LOCAL_NETWORK` для TCP/UDP в локальной сети; его нужно добавить до повышения target SDK. См. официальные страницы Android о [локальных сетевых разрешениях](https://developer.android.com/privacy-and-security/local-network-permission) и [доступе ко всем файлам](https://developer.android.com/training/data-storage/manage-all-files).

Обратите внимание: как и Windows LAN-chat, TCP-транспорт чата не шифрует соединение целиком. Тело сообщений и история зашифрованы, но служебные заголовки и LAN-вложения передаются без дополнительного транспортного шифрования. Не используйте этот режим для недоверенной сети.

## Сборка

Сначала соберите переносимое ядро: для этого нужны Go 1.26+, Android SDK и NDK `27.2.12479018`. Затем соберите и протестируйте APK в Android Studio или из терминала:

```bash
scripts/build-transfer-aar.sh
./gradlew testDebugUnitTest assembleDebug
```

Скрипт получает Croc v10.0.12 с закреплённого upstream commit, применяет Crocaun race-fix и Android-specific патчи, запускает Go-тесты, проверяет Java API и создаёт `app/libs/crocaun-transfer.aar`. `golang.org/x/mobile` намеренно закреплён в `go-core/go.mod`: gomobile требует, чтобы пакет `golang.org/x/mobile/bind` присутствовал в графе текущего модуля. Для Android привязки задан linker flag, документированный зависимостью `anet` для обхода Go 1.23+ проверки её `go:linkname`; внутреннее обнаружение Croc отключено, а совместимый Crocaun UDP-discovery реализован отдельным Android-кодом. Android-патчи запрещают вывод секрета в logcat и отключают ненужный startup DNS lookup, поскольку приложение явно задаёт relay. AAR включается в APK; GitHub Actions собирает и загружает AAR и APK как временные artifacts при push/PR.

Ежедневный запуск и ручной `workflow_dispatch` без Android-суффикса по-прежнему сверяют опубликованные стабильные Windows releases с исходным `appVersion`, создают отсутствующий Android-тег той же версии и публикуют prerelease с APK. Отдельный Android-only prerelease создаётся только при ручном запуске workflow с `android_version`, например `1.11-android.1`, и `interop_confirmed=true`. Workflow проверяет соответствующий стабильный Windows release и откажется повторно использовать существующий Android tag. Этот режим предназначен для выпуска Android-функций до следующего Windows-релиза и не изменяет Windows-репозиторий или его workflow. Не запускайте его до прохождения release gate в дорожной карте.

План этапов и условия готовности функциональных релизов находятся в [`docs/release-roadmap.md`](docs/release-roadmap.md).

## Нумерация версий

Windows-релиз остаётся базой Android-версии. Обычные синхронизированные Android-релизы используют тот же номер стабильного Windows-тега (`v1.11` → Android `versionName` `1.11`, тег `v1.11`). Между Windows-релизами разрешены отдельные Android prerelease-теги вида `vMAJOR.MINOR-android.N` или `vMAJOR.MINOR.PATCH-android.N`; например, `v1.11-android.1`, затем `v1.11-android.2`. Базовый Windows release должен существовать, быть стабильным и совпадать с `appVersion` в его исходнике. В GitHub Actions для такого релиза вводится `1.11-android.1` без начальной `v`; теги уникальны и не перезаписываются.

`versionCode` резервирует до 99 Android-only выпусков на одну Windows-базу и остаётся возрастающим при переходе к следующему numeric patch: `((major * 1_000_000 + minor * 1_000 + patch) * 100) + androidSerial`, где `androidSerial` равен 0 для обычной Windows-синхронизированной версии и 1–99 для `-android.N`. Например, `1.11` → `101100000`, `1.11-android.1` → `101100001`, а `1.11.1` → `101100100`.

GitHub prerelease содержит debug-подписанный APK для тестирования, а не production-сборку Google Play. Постоянный ключ подписи не создаётся и не хранится без отдельного решения владельца проекта.
