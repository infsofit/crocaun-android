Для самостоятельного Android-функционального релиза разрешены отдельные суффиксные теги `v<Windows-версия>-android.N`, например `v1.11-android.1` и `v1.11-android.2`. Ручной workflow проверяет совпадающую стабильную Windows-базу и уникальность tag, а также требует `interop_confirmed=true`; существующие теги и релизы никогда не переиспользуются. Этап 2 прошёл Go/AAR, Kotlin unit-test и APK gates в CI run `45534230357` на коммите `1c24baa`; пользователь подтвердил, что отправка и получение работают. Расширенные проверки неправильного пароля, Unicode-имён, отказа relay и защиты от перезаписи пока отдельно не подтверждены. Схема суффиксов поддерживается workflow, но Android-only Release ещё не опубликован; `v1.11` не изменяется. Кандидат — `v1.11-android.1` после завершения release gate.

## Этап 1 — переносимое ядро Croc (завершён)

Подготовить Go AAR поверх Croc `v10.0.12`, повторить Windows Crocaun-вывод общего секрета и порядок relay, а также применить race-патч для передачи нескольких файлов. CI проверяет golden-тесты, экспортируемый gomobile API, сборку AAR и APK и публикует их как временные Actions artifacts. Это завершено в run `45346211978`; живая Windows↔Android передача не входит в этот gate и остаётся обязательной для следующего этапа.

## Этап 2 — базовая передача файлов

Добавить отдельные Send и Receive экраны. Реализация копирует SAF-документ в app-private staging с Windows-совместимым именем; полученные данные сохраняются в уникальную staging-папку и экспортируются через SAF. Go/AAR, Kotlin unit-тесты и APK прошли CI run `45534230357`. Пользователь подтвердил работающую двустороннюю передачу Android↔Windows. Перед публикацией также необходимо проверить неверный пароль, Unicode-имя, ошибку relay и отсутствие случайной перезаписи. На этом этапе показываются только статус и ошибка передачи; foreground service и реальный прогресс ещё не входят в этап 2. После полного gate можно вручную запустить workflow с `android_version=1.11-android.1` и `interop_confirmed=true`; новый prerelease не заменит `v1.11`.

## Этап 3 — надёжная длительная передача

Первый инкремент реализован локально: Send использует Android multi-document picker, копирует выбранные файлы в одну приватную staging-папку, а одинаковые имена делает уникальными без учёта регистра; Go facade уже принимает список путей. Требуется CI-проверка этого изменения. Далее добавить пустые и вложенные каталоги, крупные файлы, повторное подключение и явные результаты передачи. Операция должна жить в foreground service, показывать реальный прогресс, предоставлять отмену и безопасно обрабатывать возврат в приложение и перезапуск процесса. Текущий Croc API синхронный и напрямую не предоставляет Android-friendly cancellation API, поэтому потребуется расширение Go facade с тестами. Проверить пакет файлов, пробелы/Unicode в именах, неправильный пароль, отмену, частичный сбой и отсутствие случайной перезаписи на Windows и Android.

## Этап 4 — LAN-обнаружение и завершение базового чата

Реализовать UDP discovery на совместимых портах, UX соединения без ручного IP, устойчивое восстановление TCP-сессии и обработку конфликтов истории. Повторить матрицу Android↔Windows для комнат, сообщений, синхронизации истории и chat-вложений. Проверить разрешения Android 11+ и поведение в Wi-Fi, hotspot и VPN. LAN-вложения остаются отдельным протоколом от основной Croc-передачи.

## Этап 5 — Internet chat и расширенные возможности

Спроектировать отдельный Android backend, совместимый с Windows Nostr chat: ключи и identity, подписи, room/event mapping, history sync, статусы собеседников и Internet file hosting. Каждый протокольный элемент сначала сравнить с Windows implementation и проверить end-to-end на тестовых аккаунтах. До этого Android поддерживает только LAN-чат, и нельзя заявлять полную совместимость чата.

## Этап 6 — готовность стабильного распространения

До production-релиза определить владельца и лицензию, проверить лицензии зависимостей и иконки, согласовать хранение секретов и политику диагностики, подготовить release signing key и процедуру его восстановления, затем проверить release APK на чистой установке и обновлении. Debug-signed prerelease не следует представлять как Google Play build. Лицензия проекта пока намеренно не выбрана.

## Правило публикации

Каждый этап сначала проходит CI и проверку на реальных устройствах. Функция включается в публичные release notes только после прохождения её gate. Если Windows-база уже опубликована, но требуется новый Android-функциональный релиз, после gate создаётся отдельный суффиксный Android tag через `workflow_dispatch` с подтверждением interop; существующие Windows и Android tags/releases не изменяются. До этого момента сборка остаётся Actions artifact.
